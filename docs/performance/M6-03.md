# Prueba de carga del gateway (M6-03)

- Fecha: 2026-11-16.
- Criterio (SPEC §9): 500 peticiones/s sostenidas, con un p95 de la latencia que agrega el gateway menor de 50 ms, sin contar el proveedor y con OPA local. Se mide sobre la red a su escala inicial: 200 entidades, 1.000 APIs y 5.000 suscripciones.
- Herramienta: `pnpm load:test` (`scripts/load-test.mjs`, `tests/load/gateway.js`). Cómo correrla: `OPERATIONS.md §5.2.2`.

## Qué se mide

- **La carga.** k6 llama a una ruta de producción por la cadena completa: TLS con certificado de cliente, token ligado al certificado, `openid-connect`, OPA, límite por suscripción, registro de acceso y de transparencia. Del otro lado está el servicio de prueba del proveedor. Cada llamada es por una persona distinta de las 1.000 que tiene ese servicio.
- **La latencia que agrega el gateway.** Es la que APISIX mide en `apisix_http_latency{type="apisix"}`: la petición completa menos la del proveedor. Se lee en Prometheus para la ruta de la prueba durante la fase sostenida. La latencia que ve el cliente se informa aparte, porque incluye la red, el reenvío de puertos de la máquina y el proveedor.
- **Pasa cuando:**
  - el p95 de la latencia del gateway es menor de 50 ms;
  - la tasa sostenida es al menos el 95 % de la pedida;
  - fallan menos del 1 % de las llamadas;
  - k6 no deja de lanzar llamadas.

## Resultados en la máquina de desarrollo

Una sola máquina: Windows 11, la VM de Docker Desktop con 12 CPU y 15,5 GB, y toda la plataforma más k6 y los servicios de otros proyectos del equipo. Son números para comparar cambios, no para dimensionar.

| Corrida | Gateway p50 / p95 / p99 | Fallidas | Observaciones |
| :-- | :-- | :-- | :-- |
| 500/s, 5 min, antes de las correcciones | 486 / 4.352 / 4.900 ms | 10,6 % | 14.887 negaciones por tiempo agotado consultando a OPA |
| 500/s, 60 s, consulta `decision`, 5 conexiones a OPA por worker | 1.223 / 4.465 / 4.900 ms | 11,3 % | 2.941 conexiones a OPA en TIME_WAIT y 426 abiertas a la vez |
| 500/s, 60 s, consulta `decision`, 64 conexiones | 174 / 2.634 / 4.527 ms | 7,2 % | 1 en TIME_WAIT. **CPU del equipo al 100 %**: APISIX 408 %, OPA 346 %, k6 95 %, Keycloak 80 % |
| **200/s, 2 min** | **4,1 / 13,3 / 38,8 ms** | **0 %** | **Pasa** |
| 300/s, 2 min | 5,2 / 27,3 / 83,0 ms | 0 % | El gateway cumple, pero k6 dejó de lanzar 680 llamadas: el cliente no alcanza |

OPA cargado directamente con k6 a 500/s (sin APISIX), la misma decisión:

| Consulta | p50 / p95 / p99 |
| :-- | :-- |
| El paquete entero (`rid/authz`, como antes) | 2,6 / 18,7 / 67,1 ms |
| Solo lo que lee el gateway (`rid/authz/decision`) | 1,6 / 4,4 / 12,4 ms |

OPA gasta unos 2,5 ms de CPU por decisión (125 % de CPU a 500/s). Es el componente más caro por llamada después de APISIX.

**Conclusión.** En esta máquina el gateway cumple el criterio hasta 200–300 peticiones/s. A 500/s la máquina entera se satura, y k6 compite con el gateway por la misma CPU. El criterio de 500/s se valida en el entorno tipo producción del cierre de M6, con el generador de carga en otra máquina.

## Hallazgos y correcciones

1. **Activación de suscripciones en una sola transacción.** Al informar OPA una revisión, el API activaba todas las suscripciones aprobadas en una transacción con límite de 5 s. Con 5.000 pendientes (la red a escala, o un atraso tras una caída de OPA) nunca terminaba, se deshacía y se reintentaba sin fin. **Ahora** activa en lotes de 100, cada uno en su transacción y cada suscripción con su evento de auditoría. Las 5.000 se activaron en un minuto. Prueba: `opa.int.test.ts`.
2. **APISIX consultaba el paquete de política entero.** El plugin `opa` pedía `rid/authz`, así que OPA evaluaba y devolvía las 31 reglas del paquete: el cliente con sus suscripciones y certificados, la ruta con sus operaciones. APISIX además parseaba todo eso en Lua en cada llamada. **Ahora** pide `rid/authz/decision`, con solo `allow`, `headers`, `status_code` y `reason`: el p95 de OPA baja de 18,7 a 4,4 ms. Pruebas: `authz_test.rego`, `desired-state.test.ts`.
3. **Conexiones a OPA abiertas y cerradas en cada llamada.** El plugin `opa` guarda 5 conexiones por worker. Pasado ese número, cada llamada abría la suya, y a 500/s quedaban miles en TIME_WAIT y conexiones que se trababan hasta el tiempo límite (3 s, y la llamada se niega). **Ahora** guarda 64 por worker y TIME_WAIT bajó de 2.941 a 1.
4. **Las APIs sintéticas no tenían servicio.** `RID_DEV_NODES` admite un prefijo (`carga-*=mock-salud:8000`) para que las 1.000 APIs de la red a escala tengan ruta.

## Dimensionamiento inicial (a confirmar en el cierre de M6)

- **OPA.** Unos 2,5 ms de CPU por decisión: 500/s piden algo más de un núcleo solo para OPA, junto a cada APISIX.
- **APISIX.** Hace TLS con certificado de cliente, valida el token y hace los registros. Es el mayor consumidor de CPU de la cadena.
- **Recomendación para el entorno de producción.** Al menos 4 vCPU por nodo de gateway (APISIX y su OPA), con el generador de carga fuera de esos nodos. El límite por suscripción se reparte entre nodos (`gatewayNodes`), así que agregar nodos no cambia lo que recibe cada aplicación.
