# SPIKE S-1 — Cabeceras de OPA visibles para otros plugins de APISIX

- Fecha: 2026-11-11 · Tiempo usado: medio día (límite: 1 día)
- Versiones: Apache APISIX 3.19.0, OPA 1.21.4
- Prototipo reproducible: `node docs/spikes/S-1/run-spike.mjs` con el stack arriba (`pnpm infra:up`). Crea una política OPA, una ruta y un servidor de captura temporales, y los borra al terminar.

## Preguntas

1. ¿Las cabeceras que pone el plugin `opa` (`send_headers_upstream`) son visibles para `limit-count` y `http-logger` en la misma petición?
2. ¿Cómo se retira `X-RID-End-User` en claro antes del upstream, para que el proveedor reciba solo el hash?
3. (Agregada en el análisis inicial) ¿En qué orden corren realmente los plugins, y qué ruta ve OPA cuando `proxy-rewrite` quita el prefijo?

## Método

Se leyó el código de los plugins dentro del contenedor (`apisix/plugins/opa.lua`, `opa/helper.lua`, `core/request.lua`) y se verificó con tráfico real:

- **Ruta de prueba:** `/salud/afiliacion/v1/*` hacia `mock-salud`, con `proxy-rewrite`, `opa`, `limit-count` (2 peticiones por minuto, clave `http_x_rid_subscription`), `response-rewrite` y `http-logger` (hacia un servidor de captura).
- **Política de prueba** (`spike.rego`): permite solo con `X-RID-Purpose: eligibility_check`. Devuelve las cabeceras de trazabilidad y dos de diagnóstico con la ruta y el `route.id` que vio OPA.
- **Peticiones:**
  - el cliente A, con cabeceras `X-RID-*` falsificadas y `X-RID-End-User` en claro;
  - el cliente A hasta pasar el límite;
  - el cliente B desde la misma IP;
  - tres peticiones con una finalidad no permitida.

## Resultados

| Verificación | Resultado |
| :-- | :-- |
| El proveedor recibe las cabeceras que pone OPA | Sí: `X-RID-Consumer-Entity`, `-Consumer-App`, `-Subscription`, `-Operation`, `-End-User-Hash` |
| Cabeceras `X-RID-*` falsificadas por el cliente | Reemplazadas por las de OPA (`sub-SPOOFED` → `sub-a`, `deleteEverything` → `getAfiliado`) |
| `X-RID-End-User` en claro llega al proveedor | **No**: se retira sin código propio (ver conclusión 2) |
| `limit-count` usa la cabecera puesta por OPA | **Sí**: el cliente A recibe 429 en la tercera petición mientras el cliente B, desde la misma IP, pasa |
| Las peticiones negadas por OPA consumen el límite | No: OPA corta la petición antes de `limit-count` |
| `http-logger` ve las cabeceras puestas por OPA | **Sí**: `subscription`, `operation` y `end_user_hash` se registran; `end_user` en claro no aparece |
| Ruta que ve OPA (`input.request.path`) | **La original con prefijo**: `/salud/afiliacion/v1/afiliados/1000000001`. `proxy-rewrite` solo cambia `upstream_uri` |
| `$upstream_uri` en el log | Incluye la query string (`?debug=1`): no debe usarse en `log_format` |
| Razón de la negación en el log | Sí, si OPA la devuelve como **cabecera de respuesta** y el log usa `$sent_http_x_rid_deny_reason` |
| 429 de `limit-count` en problem+json | No por defecto (HTML de openresty). Sí con `response-rewrite` condicionado a `status == 429` |

Del código (no probado con tráfico):
- Si OPA no responde, el plugin niega con **403**; si la respuesta de OPA no tiene `result`, responde **503**. Es decir, falla cerrado.
- `core.request.set_header` invalida la caché de `ctx.var` para esa cabecera. Por eso `limit-count` y `http-logger` leen el valor nuevo.

## Conclusiones

1. **Sí, las cabeceras de OPA son visibles para `limit-count` y `http-logger`.** No hace falta un plugin propio ni `serverless-*`. El límite por suscripción (S-2) puede usar `key_type: var` con `key: http_x_rid_subscription`.

2. **`X-RID-End-User` se retira listándolo en `send_headers_upstream` sin que la política lo devuelva.** Para cada nombre de esa lista, el plugin pone el valor que devuelve OPA y, si OPA no lo devuelve, borra la cabecera que envió el cliente. La política lee `X-RID-End-User` de `input.request.headers`, calcula `X-RID-End-User-Hash` y no devuelve el valor en claro.

3. **Orden real de los plugins.** APISIX ejecuta por fase y, dentro de cada fase, por prioridad, sin importar el orden en que se listan en la ruta:

   | Fase | Plugin (prioridad) |
   | :-- | :-- |
   | rewrite | `openid-connect` (2599) → `proxy-rewrite` (1008) |
   | access | `opa` (2001) → `limit-count` (1002) |
   | header/body filter | `response-rewrite` (899) |
   | log | `prometheus` (500), `http-logger` (410) |

   Ese orden es el que necesitamos y no hace falta cambiar prioridades.
   - El token se valida antes de quitar cabeceras.
   - Las cabeceras falsificadas se quitan antes de construir la entrada de OPA, así que la política nunca las ve.
   - OPA decide antes del límite.

4. **OPA ve la ruta completa del gateway, con el prefijo.** El `pathRegex` de cada operación en el bundle (`ARCHITECTURE.md §4.2`) debe estar anclado a la ruta pública completa (`^/salud/afiliacion/v1/afiliados/[^/]+$`), o la política debe quitar el prefijo de la ruta. Se elige la primera opción: es explícita y no depende de la configuración de `proxy-rewrite`.

5. **Formato del log de acceso.** No usar `$uri`, `$request_uri` ni `$upstream_uri`: contienen la ruta real y la query. La operación sale de `$http_x_rid_operation` y la razón de una negación de `$sent_http_x_rid_deny_reason`. Fluent Bit sigue descartando cualquier otro campo (segunda barrera).

6. **Negaciones con razón estable.** Al negar, la política devuelve:
   - el cuerpo problem+json como `reason`;
   - las cabeceras de respuesta `Content-Type: application/problem+json` y `X-RID-Deny-Reason: <razón>`, que sirven al cliente y al log de acceso (M5-03).

7. **429 en problem+json.** Se usa `response-rewrite` con `vars: [["status","==",429]]`.
   - **Pendiente para S-2/M3-05:** distinguir un 429 del gateway de uno que devuelva el proveedor, por ejemplo con `upstream_status` vacío. Si no, se reescribiría también el 429 del proveedor.

## Cambios en la documentación

- `ARCHITECTURE.md §4.1`: aclara el orden por fase y prioridad, agrega `X-RID-End-User` a `send_headers_upstream`, agrega `response-rewrite` para el 429 y deja el formato del log sin la ruta real.
- `ARCHITECTURE.md §4.2`: `pathRegex` sobre la ruta pública completa; respuesta de negación con `X-RID-Deny-Reason`.
