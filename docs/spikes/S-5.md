# SPIKE S-5 — X-Road REST como upstream y propagación del consumidor

- Fecha: 2026-11-15 · Tiempo usado: medio día (límite: 1 día)
- Versiones: Apache APISIX 3.19.0, OPA 1.21.4; protocolo X-Road REST **PR-REST 1.0.4** (`r1`)
- Prototipo reproducible: `node docs/spikes/S-5/run-spike.mjs` con el stack arriba. Crea una ruta de APISIX y una política de OPA temporales, levanta en el host un **Security Server de consumo simulado** y borra todo al terminar.

## Preguntas

1. ¿Cómo se arma la llamada REST al Security Server (URL, identificador del servicio, cabeceras obligatorias)?
2. ¿Qué cabeceras propagan el consumidor real hasta el proveedor, y cuáles llegan intactas al sistema del proveedor?
3. ¿Qué cabeceras `X-Road-*` puede usar un consumidor malicioso para cambiar el comportamiento del Security Server, y cómo se neutralizan?
4. ¿Cómo se autentica el gateway ante el Security Server?
5. ¿Qué riesgos de seguridad nuevos trae el camino X-Road?

## Método

- Lectura de PR-REST 1.0.4 (`docs.x-road.global`, "X-Road: Message Protocol for REST").
- **No se usó un Security Server real.** Hace falta un Central Server y un miembro registrado: no cabe en el tiempo de la spike y no hay un entorno público de pruebas abierto. En su lugar, un servidor en el host implementa lo que el gateway necesita del protocolo:
  - URL `/r1/{serviceId}/…`;
  - comprobación de `X-Road-Client`;
  - filtrado de cabeceras hop-by-hop y de origen (`Host`, `User-Agent`, `Server`);
  - paso intacto de las cabeceras definidas por el usuario;
  - cabeceras `X-Road-*` de respuesta.
- Ruta de APISIX con la cadena real (`rid-header-guard`, `proxy-rewrite` y `opa`) y una política mínima que devuelve las cabeceras que solo decide el gateway.

## Resultados

| Verificación | Resultado |
| :-- | :-- |
| Llamada a través del gateway | Llega al Security Server con `/r1/DEV/GOV/8999999999/REGISTRO SOCIAL-Ñ/consultaHogar/hogares/1000000001?campos=basico` |
| Identificador con espacio y `Ñ`, **literal** en `regex_uri` | Llega bien: APISIX codifica `upstream_uri` y el Security Server lo decodifica parte por parte |
| Identificador **ya codificado** (`%20`) en `regex_uri` | Llega doble codificado (`%2520`): el Security Server ve `REGISTRO%20SOCIAL-%C3%91` |
| Ruta del servicio y query | Siguen al identificador sin cambios |
| `X-Road-Client` | Siempre el subsistema del operador; uno falso del consumidor se reemplaza |
| `X-Road-Security-Server`, `-Represented-Party`, `-Id` falsos | Se borran |
| `X-Road-UserId`, `X-Road-Issue` falsos | Se reemplazan por los valores de la política (`send_headers_upstream`) |
| Cabeceras `X-RID-*` puestas por OPA | Viajan como cabeceras definidas por el usuario |
| Cabeceras `X-Road-*` de respuesta (`-Service`, `-Request-Hash`…) | Llegan al consumidor |
| `..%2F` en la ruta del servicio | 404 de APISIX: nginx normaliza la ruta, no sale de la ruta ni cambia el `serviceId` |
| Llamada negada por OPA | 403; no llega al Security Server |

## Conclusiones

1. **URL.** El upstream es el Security Server **del operador**, y la ruta reescribe el prefijo público a `/r1/{instancia}/{clase}/{miembro}/{subsistema}/{servicio}/…`. Las partes del identificador van **literales** en `regex_uri`, porque APISIX codifica `upstream_uri`. Para eso se validan al registrar la versión y otra vez en el reconciliador:
   - no llevan `/`, `%`, `?`, `#`, `$` (el `$` es especial en el reemplazo de `regex_uri`) ni caracteres de control;
   - se aceptan letras Unicode, dígitos, espacio y `. _ - : ~`, de 1 a 255 caracteres.
2. **Cliente X-Road.** El gateway es **un solo cliente** de X-Road: el subsistema del operador (`RID_XROAD_CLIENT`). `proxy-rewrite` lo fija en `X-Road-Client` y borra `X-Road-Security-Server`, `X-Road-Represented-Party`, `X-Road-Id` y `X-Road-Request-Hash` del consumidor.
3. **Consumidor real.** X-Road no tiene una cabecera para "el cliente del cliente". Por eso:
   - las cabeceras `X-RID-*` de `ARCHITECTURE.md §6` viajan como cabeceras definidas por el usuario, que PR-REST §4 pasa sin cambios;
   - OPA devuelve además, solo en rutas `xroad`:
     - `X-Road-UserId` = el hash del funcionario (`X-RID-End-User-Hash`), si lo hay;
     - `X-Road-Issue` = `rid:subscription:<id>`, que liga la llamada a la base legal y al acuerdo en el portal.

     Las dos van en `send_headers_upstream`, así que si la política no las devuelve se borra lo que mandó el consumidor.
   - `X-Road-Represented-Party` **no se usa**: las entidades consumidoras no tienen por qué ser miembros de X-Road, y declarar una representación tiene efecto legal en X-Road. Queda como extensión.
4. **Autenticación ante el Security Server.** Conexión `HTTPS` con certificado de cliente (PR-REST lo recomienda y el Security Server lo soporta).
   - El gateway presenta **un certificado propio para X-Road**, `CN=<RID_GATEWAY_CLIENT_NAME>.xroad`. Lo emite step-ca con el provisioner `rid-portal`, igual que los de M3-03, en el objeto SSL de tipo `client` `rid-ssl-gateway-xroad`.
   - El operador lo registra en su Security Server como certificado TLS interno del subsistema.
   - El certificado TLS interno del Security Server suele ser autofirmado. El gateway lo verifica contra `RID_XROAD_SECURITY_SERVER_CA` (PEM) y para el nombre del URL.
5. **Diputado confundido (riesgo nuevo).** Todas las rutas `xroad` salen con la misma identidad. Sin un control, una entidad podría publicar una versión que apunte al servicio X-Road de **otra** entidad y servirlo con la identidad del operador.
   - Regla: el miembro del `serviceId` (clase y código) debe ser el miembro X-Road de la entidad que publica.
   - Ese miembro lo registra el operador en la entidad, no la entidad misma.
   - Se valida al registrar la versión y otra vez en el reconciliador, que falla cerrado.
   - El revisor ve el `serviceId` completo en la revisión.
6. **SSRF.** El URL del Security Server sale de la configuración del despliegue (`RID_XROAD_SECURITY_SERVER_URL`), no de la versión. La versión solo guarda el `serviceId`. Así se ajusta `SPEC.md §3.1`, que preveía `securityServerUrl` por versión.
7. **Errores.** Los errores del Security Server (`X-Road-Error`, 400/500 con `type`, `message` y `detail`) pasan tal cual al consumidor, igual que los del proveedor. Convertirlos en problem+json queda como mejora: el consumidor ya distingue un error de X-Road por la cabecera.
8. **Por confirmar con un Security Server real (piloto con el operador):**
   - que las cabeceras `X-RID-*` llegan intactas al sistema del proveedor. PR-REST §4 lo dice de toda cabecera definida por el usuario, pero no nombra prefijos;
   - el formato que el operador quiera para `X-Road-UserId`. PR-REST sugiere un prefijo de país de dos letras, pero es opcional.

## Consecuencias para el backlog

- **M4-05:**
  - upstream `xroad` con solo el `serviceId`;
  - miembro X-Road de la entidad, administrado por el operador;
  - validación de caracteres y de pertenencia del miembro;
  - objeto SSL `rid-ssl-gateway-xroad`;
  - `X-Road-Client` fijo y borrado de las cabeceras de control;
  - `X-Road-UserId` y `X-Road-Issue` desde la política;
  - prueba de integración contra un Security Server simulado como el de esta spike.
- **Despliegue:** `RID_XROAD_SECURITY_SERVER_URL`, `RID_XROAD_SECURITY_SERVER_CA` y `RID_XROAD_CLIENT`. Sin ellos, las versiones `xroad` quedan en error de sincronización sin escribir nada en APISIX, como las de un nodo desconocido.
