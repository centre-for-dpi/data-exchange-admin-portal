# SPIKE S-6 — Aserción firmada del gateway hacia el proveedor

- Fecha: 2026-11-16 · Tiempo usado: medio día (límite: 1 día)
- Versiones: Apache APISIX 3.19.0 (lua-resty-openssl 1.9.0), Node.js 24 para el proveedor de prueba
- Prototipo reproducible: `node docs/spikes/S-6/run-spike.mjs` con el stack arriba. Usa el plugin `rid-assertion` (`infra/apisix/plugins`). Crea una ruta temporal y una clave nueva, levanta en el host un proveedor que verifica como lo haría uno real, y borra todo al terminar.

## Preguntas

1. ¿Puede el gateway firmar por cada llamada lo que autorizó (quién, para qué, con qué suscripción, qué operación y qué petición), de modo que la red no pueda negar después haberla autorizado?
2. ¿Quién firma (APISIX u OPA) y dónde vive la clave?
3. ¿Qué tiene que hacer el proveedor para verificarla, y con qué librerías?
4. ¿Cómo se rota la clave sin cortar el tráfico?
5. ¿Cuánto cuesta por llamada?

## Diseño probado

- **Formato.** JWS compacto ES256 (P-256) en la cabecera `X-RID-Assertion`. Es el algoritmo con soporte en las librerías estándar de Java, .NET, Python, Node y Go, sin dependencias raras.
- **Contenido.** Lo que el gateway avala, y nada más:

  ```json
  {
    "iss": "https://gateway.rid.example",
    "aud": "salud",
    "iat": 1794836052, "exp": 1794836112,
    "jti": "<request id de nginx>",
    "rid": {
      "consumer_entity": "programas-sociales", "consumer_app": "rid-app-…",
      "subscription": "…", "purpose": "eligibility_check", "operation": "getAfiliado",
      "end_user_hash": "…", "subject_ref": "…"
    },
    "req": { "method": "GET", "uri_sha256": "<sha-256 de la ruta y la query que recibe el proveedor>" }
  }
  ```

  - **Atada a la petición.** La aserción va ligada a esa petición por el método y el hash de la URI que llega al proveedor, nunca por la ruta, que lleva números de identificación. Ese número no viaja en el token, así que el token se puede archivar sin datos personales en claro.
  - **`aud`** es la entidad proveedora: una aserción para un proveedor no sirve en otro.
  - **`jti`** es el `request_id` de nginx (el mismo `gateway_request_id` del registro de transparencia): enlaza la aserción con el comprobante del titular (ADR-0016).
- **Quién firma.** Un plugin de APISIX (`rid-assertion`, prioridad 2000), justo después de `opa` (2001), firma los valores `X-RID-*` que OPA dejó. `rid-header-guard` ya quitó cualquiera que haya mandado el cliente.
- **Dónde vive la clave.**
  - Está en la metadata del plugin, compartida por todas las rutas y guardada en etcd con `encrypt_fields`. El plugin no lleva clave en ninguna ruta.
  - El portal la generaría, guardaría sellada y empujaría como ya hace con las claves TLS del gateway (`ARCHITECTURE.md §4.4`), y publicaría la parte pública en un JWKS.
  - **Sin clave**, el plugin falla cerrado (503): el proveedor no recibe una llamada sin la aserción que esperaba.

## Resultados

| Verificación | Resultado |
| :-- | :-- |
| APISIX acepta la metadata con la clave | Sí. La clave queda **cifrada** en etcd (`encrypt_fields`) |
| El proveedor recibe `X-RID-Assertion` y la verifica con el JWKS | Sí (Node `crypto.verify` con `dsaEncoding: ieee-p1363`, sin librerías) |
| Claims firmados | Entidad, aplicación, suscripción, finalidad, operación, hash del funcionario |
| Atada a la petición | Método y SHA-256 de `/servicio/afiliados/1000000001?campos=regimen`. El número no aparece en el token |
| Vida y unicidad | `exp − iat = 60 s`, `jti` = request id del gateway |
| Aserción falsa del cliente | Se reemplaza por la del gateway |
| Claim cambiado | La firma no verifica |
| Repetida en otra petición | No coincide `uri_sha256` |
| Usada ante otro proveedor | No coincide `aud` |
| Rotación | La clave nueva firma con su `kid`. Con las dos públicas en el JWKS, el proveedor verifica sin corte; al retirar la vieja, sus aserciones dejan de verificar |
| Sin clave | 503, el proveedor no recibe nada (falla cerrado) |
| Costo | No se distingue del ruido de la red local: 400 llamadas por ruta, con y sin plugin. ES256 en OpenSSL cuesta decenas de microsegundos. La medida fina va en la prueba de carga (M6-03) |
| Tamaño | ~870 bytes por llamada, una cabecera |

13/13 verificaciones del prototipo en verde.

## Alternativas descartadas

- **Firmar en OPA** (`io.jwt.encode_sign` en la política). La clave privada iría en los datos del bundle: viajaría por HTTP en cada descarga, quedaría en la memoria de cada OPA y en su caché de bundle, y cada rotación cambiaría la revisión del bundle. Expone la clave mucho más que la metadata cifrada de APISIX, y la decisión de OPA no sabe la URI que llega al proveedor después de la reescritura.
- **Solo mTLS hacia el proveedor** (M3-03). Ya autentica al gateway en el transporte, pero no deja una prueba por llamada que el proveedor pueda conservar: TLS no firma el contenido.
- **HTTP Message Signatures (RFC 9421).** Es el estándar más preciso para firmar la petición, pero hoy tiene poco soporte en las librerías de los lenguajes de las entidades. Queda como evolución si la red lo adopta.

## Hallazgos para otras historias

- **Keyring de APISIX (M6-01).** `encrypt_fields` cifra con el `data_encryption.keyring` de APISIX, cuyo valor por defecto es público, y con él también se cifran las claves TLS que ya están en etcd. Cada despliegue tiene que configurar su propio keyring (un secreto), o el cifrado en reposo no protege nada.
- **Cuerpo de las peticiones POST.** El prototipo ata la aserción a la URI. Para las operaciones con cuerpo (como la verificación con titular en el body, ADR-0017) se puede agregar `body_sha256`: `rid-data-subject` ya lee el cuerpo en esas rutas.
- **Errores del plugin.** Llegan al log de errores enmascarado (`fluent-bit-errors`, M5-01).

## Conclusión

Es viable y barato. Se recomienda que firme el gateway, con la clave gestionada por el portal (ADR-0024). La implementación completa queda como historia: reconciliación de la clave, JWKS público, configuración por versión o por red, guía del proveedor y verificación en el mock.
