# User manual with screenshots — design

Date: 2026-11-19 · Status: draft for approval

## Intent

The full walkthrough ([docs/guides/walkthrough.md](../../guides/walkthrough.md), Spanish in
`docs/es/guides/`) already holds the right content: every step real people take so that one entity
publishes an API and another consults it. What is missing is a **polished user manual** of that
same path: "bien bonito", with **a screenshot of the portal for every step**, that the operator
and the entities can follow on their own (and that can be projected in a session).

## Goals

- A user manual that follows the walkthrough's sections and order: operator team → provider
  onboarding → operator approval → invitations → node → publish API → operator approves API →
  consumer (onboarding, application, mTLS certificate, access request) → provider decides →
  first lookup → troubleshooting.
- Every portal step has a real screenshot of the running portal, with the element to click or
  fill **highlighted** (outline + numbered badge) and the numbers matching the step's text.
- Screenshots are **generated by a script** that drives the real flow against the local stack, so
  they can be regenerated with one command when the UI changes.
- A presentation page with the look of the existing guides, published as a private Artifact the
  user can share, and kept in the repo.

## Non-goals

- Covering every screen of the portal (regulator console, indicators, audit, analytics, bootcamp,
  platform users beyond the one step, etc.). Only the walkthrough path. A per-role reference can be
  a later document.
- Changing the product UI.
- Videos or animated GIFs.
- Replacing the walkthrough: it stays as the technical reference (full installer tables, instant
  API configuration file, curl by hand).

## Anti-goals (a failure even if it technically works)

- Screenshots that go stale silently, or that are mocked/edited images of screens that do not exist.
- Screenshots showing real personal data, or legible secrets (TOTP QR codes, client secrets,
  enrollment tokens) — even synthetic ones: they are blurred.
- A manual that reads like the walkthrough with pictures pasted in: it must read as a manual
  (one action per step, short text, the picture carries the detail).

## Constraints

- Project rules (CLAUDE.md): official docs in English with the Spanish version at the same path
  under `docs/es/`, updated in the same commit (ADR-0027); UI is Spanish by default; only
  OSI-approved dependencies (`pnpm license:check`); WCAG 2.1 AA for the page.
- Data: only synthetic data, the walkthrough's example values (*Civil Registry* /
  `civil-registry` / NIT `900000100`; *Ministerio de Bienestar de Wakanda* / `bienestar-wakanda` /
  NIT `900000200`; API *Certificado de afiliación* / `certificados-afiliacion`).
- Artifact size: page and each file ≤ 16 MB, ≤ 64 MB per publish.
- The manual goes public (GitHub Pages): nothing in it or its screenshots may name the demo
  deployment's domain, real people or real entities.
- Commit locally only; no push (standing instruction).

## Approaches

| | Approach | Trade-off |
| :-- | :-- | :-- |
| **A (chosen)** | HTML page in the guides' design + screenshots captured by a Playwright script, Markdown source in the repo, published as an Artifact | Best look and the only one that keeps screenshots current; not editable as a document |
| B | Claude Docs document with uploaded screenshots | Editable, commentable, exports to PDF/Word; little control over the design |
| C | Claude Design canvas | Good for a one-page poster, wrong for a 40-step manual read top to bottom |

The user picked **A** (2026-11-19).

## Design

### 1. Content (Markdown source)

- `docs/guides/user-manual.md` (English, official) and `docs/es/guides/user-manual.md` (Spanish).
- Same sections and order as the walkthrough. Each section opens with **who** does it (role chip)
  and **what they need before starting**. Each step: one action, a short instruction, the
  screenshot, optionally a *Tip* or *Attention* box.
- Dropped from the walkthrough: "What the product still lacks" and historical remarks (P-xx,
  "before P-08", installations without update). Kept: "Before you start", the example values, the
  troubleshooting table (portal-facing rows first).
- Terminal-only steps (grant the first platform role, install the node, add the service, create
  the CSR, first lookup) are shown as **terminal blocks** with the commands and the expected
  final message the walkthrough documents (e.g. "El nodo está en línea"); no invented output.
  The instant-API detail (view, read-only user, service YAML) is summarised and links to the
  walkthrough §5.3.
- Images referenced from the Markdown as `![alt text](img/user-manual/NN-slug.jpg)`, alt text
  describing what the screen shows (accessibility).

### 2. Screenshot capture

- A Playwright script in `apps/web/e2e/manual/` (its own config or project so `pnpm test:e2e`
  does **not** run it), started with a root command `pnpm docs:manual`.
- Runs against a **freshly reset** local stack (`pnpm infra:reset`, `pnpm infra:up`,
  `pnpm db:migrate`, `pnpm db:seed`), because it uses the walkthrough's fixed names; if
  `civil-registry` already exists it stops with a message saying to reset.
- Drives the whole path with real accounts, reusing the e2e helpers: self-registration through
  Keycloak + Mailpit (`onboarding.ts`), second-factor enrollment (`helpers.ts`), the simulated
  node for the node steps (`mock-node.ts`), CSR generation (`csr.ts`), approvals as the seeded
  operator/regulator demo users where the operator is needed. The first `platform_admin` is shown
  as the CLI step plus a screenshot of **Operator console → Platform roles and accounts**.
- Runs twice: Spanish UI → `docs/es/guides/img/user-manual/`, English UI (`/en`) →
  `docs/guides/img/user-manual/`. Same file names in both. *(Builder's call:)*
  the stack is reset before each language run (`pnpm docs:manual` does reset → up → migrate →
  seed → capture, per language), so each run uses the example values of its own walkthrough
  (the English run shows "Ministry of Welfare of Wakanda").
- *(Builder's call:)* the node and API values in the manual follow what the test fixtures really
  serve — the simulated node's service path `/salud` and the mock contract
  `infra/mock-providers/salud/openapi.yaml` (lookup `/afiliados/{id}`) — so text and screenshots
  agree and the automatic validations pass. The manual says they are example values; the
  walkthrough keeps its own.
- Annotation: the script records the target elements' boxes (in % of the image) in a
  `manifest.json` beside the images; the page draws the outline and numbered badge over the clean
  image as HTML buttons (so hotspots are clickable and accessible, and the style lives in one
  place). QR codes, client secrets and tokens are blurred into the image before the screenshot.
- Fixed viewport (1440×900, scale 1), screenshot of the viewport or clipped to the relevant
  region. **Images are committed, compressed** (user's decision): Playwright's own JPEG output
  (quality ≈ 85, no new dependency), target ≈ 2–4 MB per language.
- Resetting the local stack on this machine is allowed (user's decision); the capture command
  says so in its help text because it wipes the local volumes.

### 3. Presentation page

- `scripts/user-manual-html.mjs`, in the spirit of `scripts/walkthrough-html.mjs`: takes the
  `<head>`, styles, top bar and script of `entities.html` of the same language so all guides keep
  one design, and adds the manual's components: step cards with numbers, role chips per section,
  figures with caption and click-to-enlarge (lightbox, keyboard accessible), Tip/Attention boxes,
  terminal blocks with copy button, progress in the contents rail, projection mode (already in
  the guides).
- Interactive features, from the best-practice review of 2026-11-19 (GOV.UK step-by-step
  navigation, Diátaxis how-to guides, Google developer style guide on images and alt text, W3C
  WCAG 1.4.13, eBay/Pearson accessible lightbox and hotspot patterns, NN/g help heuristic):
  1. **Journey map:** a numbered step-by-step overview at the top (GOV.UK pattern), each step
     tagged with its role; steps that run in parallel are marked "and".
  2. **"Who am I?" role filter:** operator, provider entity, consumer entity. It highlights that
     role's steps and dims the others (never hides them: it is one journey). Remembered in
     `localStorage`, wrapped in try/catch.
  3. **Progress checklist:** "Done" per step, progress shown in the contents rail, remembered in
     `localStorage`; a "reset progress" button.
  4. **Numbered hotspots on screenshots:** the badges are buttons; activating one scrolls to and
     highlights the matching sub-step in the text. Click or Enter, never hover-only (WCAG 1.4.13).
  5. **Lightbox:** native `<dialog>` with `showModal()`: focus moves in, Escape closes, focus
     returns to the image.
  6. **Terminal blocks:** copy button; tabs per OS (Linux/macOS, Git Bash, PowerShell) where the
     walkthrough has variants, with the chosen OS kept for the whole page.
  7. **Search:** a client-side filter over steps and troubleshooting rows; each troubleshooting
     symptom links back to the step it belongs to.
  8. **Deep links:** every step has an anchor and a "copy link" button, so the help desk can send
     "step 6.2".
  9. **Print stylesheet:** everything expanded, images inline, interactive controls hidden, so
     "Print → PDF" gives a usable handout.
  10. Projection mode (already in the guides).
- Writing rules from the same review: the text must stand without the image (images never carry
  information that is not in the text); alt text ≤ 155 characters, about what the reader must
  notice in that screen; screenshots cropped to the relevant region; one annotation style for the
  whole manual; no text burned into screenshots beyond the numbered badges (explanations go in
  captions); no autoplay video or GIFs. The manual stays a how-to guide: concepts are linked to
  the operator guide, not explained inline.
- Output: `docs/guides/user-manual.html` and `docs/es/guides/user-manual.html`, with images by
  relative path, so they work opened from the repo and as a multi-file Artifact.
- The Spanish page is published as a private Artifact (images as published files); the English
  one too, as a separate Artifact. Links handed to the user.

### 4. Wiring

- Link the manual from both walkthroughs and from the docs site index (`docs/site`).
- **Public GitHub Pages site too** (user's decision): `scripts/docs-site.sh` also copies
  `docs/guides/img/**` and `docs/es/guides/img/**`, and `.github/workflows/pages.yml` triggers on
  those paths as well.
- Root scripts: `docs:manual` (capture) and the HTML build (or one command doing both).
- No BACKLOG story (documentation outside the milestones); commit as `docs(guides): ...`.

## Left to the builder

- Exact list and naming of the screenshots per step; which ones are clipped vs full viewport.
- Overlay styling (must be readable in the screenshot and consistent with the page's palette).
- How the capture script is split into steps/files and how it waits for async states (validations,
  node online, gateway route live).
- Whether the HTML generator shares code with `walkthrough-html.mjs` or stands alone.
