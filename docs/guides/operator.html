Part I · The platform

1The network on one page

The Data Exchange Network lets a public entity query another entity's data without copying it, with explicit permission, for a declared purpose and leaving a trace of every request.

The data stays at each entityThe central gateway only passes the request and the response through. It does not store content, neither in a database nor in logs.
Nobody gets in without permissionEach access is a subscription: an application, to an API, for a purpose, approved by the data steward of the entity that owns the data.
Everything is auditedEvery change goes into a hash-chained audit log that a timestamping authority seals daily.
Citizens see who queried themWhat for and when, with a receipt that anyone can verify without trusting the portal.
Only free softwareOSI-approved licenses: no license costs and no vendor lock-in.
Reusable in another countryEverything specific to a country (authorities, documents, sectors, legal framework) is in config/country/<code>.yaml; co.yaml (Colombia) is the reference.

The second factor is a TOTP code from an authenticator app. Nobody approves what they themselves requested: the portal separates duties.

3Architecture: two planes

The governance plane decides who can do what and turns that into configuration. The data plane serves each call with the latest configuration and the latest policy it received. If the portal goes down, traffic between entities keeps flowing.

The portal never configures the gateway "by hand"

A reconciler works out from the database how APISIX, Keycloak, OPA and the hub should be set up, and adjusts them. It is idempotent: if something drifts or gets lost, the next pass (every 5 minutes, or when the API restarts) repairs it. That is why nobody fixes APISIX or Keycloak by hand.

4The components, one by one

For each one: what it does, what happens if it goes down and what it stores. In the pilot, they all run as containers on the same server.

If it goes down: traffic keeps flowing traffic keeps flowing, no changes traffic stops backed up

Entry

Traefik

bundled proxy · 443 and 80

Receives everything on 443. For the portal name it terminates HTTPS (Let's Encrypt or your own certificate) and routes by path: / web, /api/v1 API, /auth Keycloak. For the gateway name it does not open the TLS: it passes it untouched to APISIX, so that mTLS is end to end. It rate-limits requests by source address and never exposes /api/v1/internal or /api/v1/opa.

If down
nobody gets inNeither people nor systems.
Stores
The Let's Encrypt certificate. No access log, for privacy.

Governance plane

Web portal

Next.js

The interface for everyone: catalog, interactive documentation, consoles for the operator, the regulator, the entity and the audit. It does not decide permissions: the API does.

If down
traffic keeps flowingNo portal.
Stores
Nothing.

Portal API

NestJS

The brain. It runs the workflows (registration, publication, request, approval), checks role and entity on every request, and records every change in the audit log. In the background it reconciles APISIX, Keycloak, OPA and the hub; signs certificates; seals; sends emails; expires subscriptions and certificates; rotates every 90 days the key the gateway uses to sign its assertions, and publishes the public keys (JWKS).

If down
traffic keeps flowing, no changesIt keeps going with the latest published policy.
Stores
Nothing of its own: everything is in PostgreSQL.

PostgreSQL

database

Single source of truth: entities, people and roles, APIs, applications, subscriptions, audit log, transparency log and job queues. The audit log is insert-only, even for the database owner.

If down
traffic keeps flowing, no changesThe governance plane stops.
Stores
backed upEverything.

pgBackRest

database backups

Archives every PostgreSQL change within a few minutes (at most 5 minutes of loss), takes a full backup each week and a differential one each day, and keeps four weeks. The repository is encrypted. It can return to the latest state or to an exact point in time, with a restore tested in CI.

If down
traffic keeps flowingNew changes wait to be archived.
Stores
backed upThe encrypted repository. It is copied off the server.

Keycloak

identity · OpenID Connect

It authenticates, it does not authorize: roles live in PostgreSQL. Three realms: den-portal (people, with a second factor), den-gateway (the entities' applications; the portal creates their clients) and den-citizens (simulated citizen identity; in production, the country's own).

If down
no new tokensNobody can sign in. Tokens last 5 minutes: after that, calls fail.
Stores
Users and clients, in PostgreSQL.

step-ca

the network's certificate authority

Signs the applications' certificates (from the CSR the entity uploads: the private key never leaves the entity), the gateway's and the nodes'. Only the API talks to it.

If down
traffic keeps flowingNo certificates are issued; current ones keep working.
Stores
backed upThe CA keys. Losing them invalidates every certificate.

TSA

RFC 3161 timestamping

Seals the audit log's daily anchor and the transparency log's batches: it proves they existed at that moment and that nobody rewrote them.

If down
traffic keeps flowingSeals are queued and applied when it comes back.
Stores
Its key. In production, the country's accredited TSA is used.

Email

Mailpit in the pilot

Captures all email (invitations, notifications, account verification, anchors to the regulator, alerts) and shows it at /mail, behind a password. In production, the operator's SMTP.

If down
traffic keeps flowingNo emails go out.
Stores
The pilot's emails.

ClamAV

antivirus · optional

Scans every uploaded document (appointments, data exchange agreements) before storing it. An infected one is rejected; the log keeps the virus signature and the hash, never the name or the content. It updates its signatures from the internet.

If down
traffic keeps flowingDocuments cannot be uploaded: it fails closed.
Stores
Its virus signatures.

Data plane

APISIX

gateway

Every call between entities goes through here. It requires the application's certificate (mTLS), validates the token, strips the headers only the gateway may set, asks OPA, applies the subscription's limit, and forwards to the provider with the traceability headers and a signed assertion of the call. It does not store bodies.

If down
traffic stops
Stores
Nothing; its configuration is in etcd.

etcd

gateway configuration

The gateway's routes, upstreams and certificates. It is rebuilt from PostgreSQL.

If down
traffic keeps flowing, no changesAPISIX keeps going with what it has in memory.
Stores
Rebuildable configuration.

OPA

Open Policy Agent

Decides each call with the policy the portal publishes: current subscriptions, purposes, operations and certificate fingerprints. It answers "yes" or "no, for this reason" (no_subscription, purpose_not_allowed…). Without a policy, it denies everything: it fails closed.

If down
traffic stops
Stores
The latest policy, on disk: if it restarts without the portal, it keeps deciding with it. It refreshes it every 10–20 s.

WireGuard hub

51820/udp

The central end of the encrypted tunnels that the kit's nodes open from each entity's network, from the inside out: the entity opens no inbound ports. A node cannot reach other nodes or the platform.

If down
node APIs go downExisting APIs keep working.
Stores
The latest state of the tunnels.

Fluent Bit · transparency

from the gateway to the portal

Carries the record of every authorized request for a person's data: who, what for, under which subscription, and the data subject's pseudonym, never their document number.

If down
traffic keeps flowingRecords wait in its on-disk buffer.
Stores
Temporary buffer.

Fluent Bit · analytics and OpenSearch

optional

A second privacy barrier: it only lets allowed metadata through (no real path, no query string, no body) and stores it for the usage indicators.

If down
traffic keeps flowingThat metadata is lost.
Stores
Usage metadata, expendable.

Prometheus, Alertmanager and Grafana

optional · /grafana

They measure the gateway, the API and OPA. Nine alerts email the operator: many 5xx responses, high latency, service down, stale policy, failed reconciliation, nodes offline, certificates about to expire and a backed-up queue.

If down
traffic keeps flowingNo alerts.
Stores
30 days of metrics.

Contract runner

Schemathesis

When an entity submits an API for review, it tests the API's OpenAPI contract against the sandbox. The operator only approves once the checks pass.

If down
traffic keeps flowingContracts are not tested.
Stores
Nothing.

Pilot tooling (does not go to production)

  • Test providers (mock-salud, mock-socioeconomico): they simulate two entities with synthetic data.
  • Reference citizen app (/citizen-app): shows what the country's real citizen app must implement.
  • Seed data: three fictitious entities and the demo users.

5How everything flows

Publishing an API

draft→ in review→ approved by the operator→ approved by the regulator · if sensitive→ published
  1. The entity's publisher uploads the OpenAPI contract and states where the service lives, which data it exposes, the legal basis and the allowed purposes.
  2. When it is submitted for review, the portal tests connectivity through the gateway and the contract against the sandbox.
  3. The operator reviews the API's details and data minimization. If the classification is sensitive, the regulator approves too.
  4. Once published, the route appears in the gateway within seconds, closed: with no subscriptions, nobody gets in.

Requesting and granting access

pending provider→ pending regulator→ approved→ active→ suspendedrevokedexpired
  1. The consumer's developer creates an application: it gets a secret (shown only once) and uploads its CSR to obtain its certificate.
  2. They request access: API, operations, purpose from the catalog, details, legal basis, validity period and data exchange agreement.
  3. The provider's data steward approves (and can reduce operations, limit or validity period), rejects, or asks for more information.
  4. Within 60 seconds OPA has the new policy and the subscription becomes active. Suspending or revoking also takes effect within 60 seconds.

Accountability to citizens

Every authorized request for a person's data is recorded in the transparency log with the data subject's pseudonym. Every 10 seconds the records are grouped into batches signed by the operator and sealed by the TSA. From their folder, citizens see who queried them and what for, receive notifications, and download a receipt that anyone can verify without trusting the portal, with the open verifier den-verify-receipt.

6Security and privacy

What the platform guarantees, and how.

Only identified systems reach the gatewayMandatory mTLS with certificates from the network's CA; 5-minute tokens bound to the certificate.
Only approved accessOPA decides each call with the current subscriptions, and fails closed.
Content is not storedNeither the gateway nor the logs store bodies. Paths and query strings are masked, with two barriers: APISIX and Fluent Bit.
The data subject is not exposedOnly a keyed pseudonym (HMAC), in the transparency log; never in the analytics.
Nobody rewrites historyHash-chained, insert-only audit log, with a daily anchor sealed by the TSA and sent to the regulator.
Protected accountsSecond factor for critical roles, request rate limits, and the owner is notified when a credential changes.
Server-side authorizationEvery endpoint checks role and entity. The full matrix is in AUTHZ.md, and tests verify it.
Isolated entitiesEach provider using mTLS accepts only the gateway certificate issued for it; a node cannot reach other nodes.
The provider knows the request is legitimateAn assertion signed by the gateway on every call (ES256), bound to the request and to that provider, verifiable with a public JWKS. A forged header from the client is discarded.
Reviewed against standardsOWASP ASVS level 2, chapter by chapter (docs/security/ASVS-L2.md), and WCAG 2.1 AA on all 42 screens, in Spanish and in English (docs/accessibility).
Part II · Installing the operator's infrastructure

7Server requirements

A single Linux server running the whole central platform: this is the pilot topology, for go-live, the bootcamp and demos. Production with high availability (Helm charts) is a separate exercise.

vCPU4–8minimum 4
RAM16 GBminimum 8 GB, without observability
SSD disk100 GBminimum 60 GB
SystemUbuntu 24.04or 22.04, Debian 12, RHEL/Rocky 9 · kernel ≥ 5.6 · x86_64 or arm64
Where these numbers come from

At rest, the full stack uses about 2.3 GB of RAM (Keycloak ~650 MB, OpenSearch ~670 MB, APISIX ~190 MB, API ~150 MB, web ~120 MB, the rest under 70 MB each). The antivirus, if enabled, adds ~1.2 GB. The real peak is building the portal and API images during installation and on every update: 3–4 GB more for 10–20 minutes. The images take ~15 GB, and the build cache grows with each update (it reached 17 GB in the pilot). Kernel ≥ 5.6 includes WireGuard; without it, the hub uses wireguard-go, which works but performs worse.

Before you start

8Install

git clone <repository-url> den && cd den
sudo ./install.sh

The script checks the server, asks the questions in steps 2 to 6, shows a summary and asks for confirmation before touching anything. It then builds and starts everything (10–20 minutes the first time) and checks that it works. If Docker is missing, it offers to install it.

Step1

Server check

No questions. System, CPU, RAM, disk, Docker and Compose ≥ 2.26, /dev/net/tun, free ports and DNS. It stops if anything essential is missing.

Step2

Country

The code of config/country/<code>.yaml. For example, co (Colombia).

Step3

Portal and gateway names

Just the name, without https://. The gateway's defaults to gw.<portal> and must be different from the portal's.

Step4

Entry proxy and portal certificate

1Bundled proxy (recommended): the installer puts Traefik on 80/443.
2I already have Traefik: it joins its Docker network, and the operator configures the routes.
1Let's Encrypt: optional contact email; port 80 must be reachable.
2Your own certificate: paths to the certificate (full chain) and to the private key, in PEM. It must come from a recognized public CA, because the API and the web also call the portal by its name.
Step5

Observability and antivirus

Two yes-or-no questions:

  • Observability (OpenSearch, Prometheus, Alertmanager, Grafana): usage indicators, email alerts and the operator's dashboard. Yes, if the server has 16 GB. You can do without it: it does not affect traffic, the audit or transparency.
  • Document antivirus (ClamAV): scans every uploaded document before storing it. Yes, if the server has 8 GB. It adds ~1.2 GB of RAM and downloads its signatures from the internet.
Step6

Demo users' password

12 characters or more (Keycloak's password policy). Pressing Enter generates a random one. Choose one yourself if you are going to share it at the bootcamp.

Step7

Secrets

No questions. It writes .env (mode 600) with all the secrets, randomly generated: databases, signing keys, pseudonym key, WireGuard hub key, backup encryption key, internal tokens.

Step8

Server preparation

No questions. It creates the Docker network and sets vm.max_map_count for OpenSearch. If it detects ufw or firewalld, it offers to open the ports.

Step9

Build and start

No questions. It waits until every service is healthy.

Step10

Checks

That the API responds; that the OPA policy is not publicly exposed; that Keycloak responds; that OPA already has a policy; that the gateway presents the network's certificate.

Keep .env off the server, encrypted

Without it, the data cannot be recovered and receipts already issued cannot be verified. Running ./install.sh again never regenerates it: it reuses its secrets and answers.

In production there are no seed users: the first platform_admin is whoever signs in first with the address in DEN_BOOTSTRAP_ADMIN_EMAIL, verified by Keycloak, while the network has none. This is audited, and the value is deleted afterwards.

Part III · Operations

11Day to day

sudo ./install.sh statusStatus of the containers and the installation checks.
sudo ./install.sh credentialsDemo users, Keycloak administrator, test mailbox and Grafana.
sudo ./install.sh otpCurrent second-factor code for the demo users with a critical role.
sudo ./install.sh logs apiLogs for one service (api, apisix, keycloak, edge…), or for all of them with no argument.
sudo ./install.sh backupFull backup and a copy in backups/<date>/: dumps of den and keycloak, the (encrypted) backup repository, the volumes for the CA, the TSA, documents and the citizen app, and .env. The files go off the server. Daily backups already run on their own.
sudo ./install.sh restoreRestores the database to the latest archived state; with a point in time ("2026-11-20 14:30:00-05"), to that moment. It stops and starts everything.
sudo ./install.sh updateBackup, git pull --ff-only, rebuild and restart.
sudo ./install.sh stopStops everything without losing data; start starts it again.
  • Every day: healthy services, nothing out of sync with the gateway (Operator console → Gateway sync), an intact audit chain (Console → Audit → "Verify integrity") and an intact transparency log.
  • Alerts: with observability enabled, they arrive by email (in the pilot, at /mail). The dashboard is at /grafana/.
  • Operator runbook (docs/RUNBOOK.md): registering an entity up to its first published API, suspension and offboarding; incidents with severities and a procedure for each case; rotation of the intermediate CA, planned and emergency; mass certificate revocation.
  • Mass certificate revocation: Console → "Mass certificate revocation", only platform_admin with a second factor. It filters by entity, by issue date and by intermediate, shows a preview, and revokes only if the set has not changed. Each certificate stops working within 60 seconds and the developers receive a notification. It cannot be undone.
  • Gateway signing key: the portal rotates it on its own every 90 days; the previous one stays in the JWKS so that archived assertions keep verifying. If it is compromised, rotate it immediately as compromised (POST /api/v1/admin/gateway-signing-keys/rotate) and notify the providers (runbook §2.2).
  • When updating a pilot installed before automatic backups existed, update adds the backup encryption key to the .env and says so: save the copy of .env again.
  • Never fix APISIX or Keycloak by hand: the reconciler reverts it. If something does not add up, check "Gateway sync" in the operator console and retry from there.

SymptomWhat to do
"Ports in use"Another service is using 80/443 (ss -ltnp). Stop it, or choose "I already have Traefik" in step 4.

What is already tested and what is missing

  • Resilience, tested: with the portal down for 45 seconds, both allowed and denied calls kept going, each as it should. OPA and APISIX restart without the portal. When it came back, the transparency log had every request from the outage, and a revocation reached the gateway in 18 seconds.
  • Backups, tested: restore is tested in CI: loss of the volume, return to a point in time, and a repository that is unreadable without its key.
  • Load, partly tested: on the development machine, the gateway serves 200 requests per second with a p95 of 13 ms over the network at its initial scale (200 entities, 1,000 APIs, 5,000 subscriptions). The target is 500 per second with a p95 under 50 ms. It will be validated in a production-like environment, with the load generator on another machine.
  • Helm charts, not yet installed: they are complete and statically validated. They will be installed for the first time in the operator's environment, together with a restore from its object storage.

14Questions that often come up

Can the operator see the data being exchanged?

No. The gateway passes it through without storing it, and the logs only hold masked metadata.

What happens if the portal goes down?

Traffic between entities keeps flowing with the latest configuration and the latest policy. Only changes stop: new approvals and publications. It is tested: with the portal down, calls keep going; OPA and APISIX restart without it, and when the portal comes back it recovers the transparency records from the outage.

How does the provider know a request really comes from the gateway?

Through the signed assertion (X-DEN-Assertion): one JWS per call, bound to the method, the URI, the body and that provider, which it verifies with the portal's public keys. An assertion the client tries to slip in is discarded. The entity guide has verification examples in Node.js and Python.

How much traffic can it handle?

On the development machine, 200 requests per second with a p95 of 13 ms added by the gateway. The target, 500 per second, will be validated in a production-like environment. Capacity grows with more gateway nodes: each one counts limits on its own, and the policy gives it its share.

Is the portal available in English?

Yes, fully, in addition to Spanish, which is the default language. The emails and the citizen app are bilingual too.

Does an entity have to open inbound ports?

Not if it uses the kit: the node opens the tunnel outbound (UDP 51820). With an existing API, the entity must allow the gateway to reach it.

Can it be integrated with X-Road?

Yes: the gateway can use an operator's Security Server as an X-Road client.

Who approves access to sensitive data?

The data steward of the entity that owns the data and, in addition, the regulator.

How do you prove the audit log was not altered?

With the console's integrity check and with the daily anchor the regulator receives by email, sealed by an independent TSA.

Can it be taken to another country?

Yes, without changing code: a new config/country/<code>.yaml and the translation texts. It is tested with an "example country" brought up from the example.yaml template: the full demo passes with its own sectors, purposes and document type.

Technical details are in the repository's docs/ARCHITECTURE.md, docs/DEPLOYMENT.md, docs/OPERATIONS.md and docs/RUNBOOK.md. What each entity must provide is in the entity guide.
