Before the day

1What it means for an entity

As a providerIt publishes an API over its data. Its data steward decides who gets access, for what purpose, to which operations and for how long. For every request, it knows who made it and why. The data is never copied to the platform.
As a consumerIt finds APIs in the catalog, creates an application with its credentials and requests access by declaring a purpose. Once the provider approves, its systems send requests through the gateway.
Toward citizensCitizens see which entity queried their data and why. Every request must serve a legitimate, declared purpose.

2People the entity must appoint

entity_admin
Head of IT or of the data office

Requests the entity's registration, invites its people, assigns roles and manages the kit's nodes.

data_steward2nd factor required
Data steward (formal appointment)

Approves, rejects, suspends and revokes access to the entity's APIs.

api_publisher
Technical lead

Registers the APIs and submits them for review.

app_developer
Developer of the consumer system

Creates applications, manages credentials and requests access.

  • Each person needs their own institutional email address: the account is verified by email, and invitations are sent to that address.
  • The second factor is set up with an authenticator app (FreeOTP, Aegis, Google Authenticator or any other TOTP app) on the person's phone.
  • Document: the act appointing the data steward and the technical lead, as a PDF. It is attached to the registration request.

3What a consumer provides

WhatDetails
Consumer systemThe server or application that will send the requests. It must make HTTPS calls with a client certificate (mTLS): any modern language can (curl, Java, .NET, Python, Node).
Outbound internet443/tcp to the gateway name and the portal name.
A place for secretsThe certificate's private key and the application secret: never in code or in a repository.
opensslTo generate the private key and the certificate signing request (CSR). The private key never leaves the entity's server.
OfficialAPIs with personal data require X-DEN-End-User: the username or institutional email of the person making the request. It is only recorded as a hash.

4What a provider provides

Every provider connects through the node, which is installed inside its network and opens an encrypted tunnel outbound: outbound 51820/udp and 443/tcp, no inbound ports. Behind the node sits either the entity's own API (canal mode) or instant APIs over views in its database (completo mode: SQL Server, PostgreSQL, MySQL or Oracle). Entities that already publish on X-Road come in through the operator's Security Server.

Provider guide

The server and network requirements, installing the node, publishing an API and what the service receives with each request are in the provider guide in the kit repository: docs/guides/providers.md, with its presentation version providers.html.

The gateway's signed assertion

If the country has it enabled, every request arrives with X-DEN-Assertion: an ES256 JWS from the gateway stating who is making the request, what for, under which subscription and which request it belongs to (the method, the hash of the path and, if there is one, of the body). The entity can keep it as proof. It is verified with the network's JWKS, https://<portal>/api/v1/gateway/jwks, by checking the signature, aud (the entity), iss (the gateway), exp, the hashes of the request received (the body hash on every POST, PUT and PATCH, and on any other request that carries a body, a GET or a DELETE too, whatever its type; it is computed over the bytes exactly as they arrived, before parsing them) and that the jti is not repeated. The Node.js and Python examples are in docs/guides/entities.md (§3.2).

On the day

6Check the network from the entity's server

The operator hands out the platform's two names, the portal's and the gateway's, and the entity-check.sh script. It only needs bash, curl and openssl. Run it on the server that will send the requests, or on the node's server.

chmod +x entity-check.sh
./entity-check.sh check <portal> <gateway>

It checks DNS, outbound HTTPS to the portal and to the gateway, and that the gateway's certificate verifies against the network's root. It saves the root to ./den-network-ca.pem.

7Registering the entity and its people

  1. The future entity_admin goes to https://<portal>, creates an account and confirms the email address.
  2. They request the entity's registration: its details, the appointed leads and the appointment document. The operator reviews and approves it. If the entity has already been onboarded by a formal act, the operator registers it directly.
  3. The entity_admin invites each person by email and assigns their roles. Each invitee creates an account with that same email address and accepts the invitation.
  4. The data_steward sets up the second factor the first time the portal asks for it.

9Consumer entity: first request

  1. Try the sandbox first. The app_developer creates an application of type sandbox. Its requests for access to APIs that have a sandbox are approved instantly, and it calls /sandbox/…, with synthetic data.
  2. Save the secret shown when the application is created: it is shown only once.
  3. Application certificate, on the entity's server. Paste the CSR into the application's page → Client certificate (mTLS), download the certificate and save it as <client_id>.crt next to the private key. 
    ./entity-check.sh csr <client_id>   # creates <client_id>.key (600) and <client_id>.csr
  4. Request access: in the catalog, open the API → Request access. Choose the application, the purpose, the details, the legal basis, the operations, the validity period and the data exchange agreement. In production, the provider's data_steward approves it, and the regulator too if the data is sensitive.
  5. Call. The script requests the token, sends the request with X-DEN-Purpose and X-DEN-End-User, and explains the response. The exact URLs are on the API's page and on the subscription's page. 
    CLIENT_SECRET=... ./entity-check.sh call <portal> <gateway> <client_id> \
  /sandbox/<entity>/<api>/v1/<resource> <purpose> <official>
  6. With the production application, repeat steps 2 to 5 with the real path (without /sandbox), once the request is approved.
Integration guide in the portal

Each application's page includes a complete program in curl, Python, Node.js, Java and C#: it requests the token with the certificate and calls with the network's headers. The secret is read from the DEN_CLIENT_SECRET variable, never from the code.

11The entity's commitments

A real purposeOnly send requests for the declared and approved purpose. Every request is recorded in the log, and the citizen sees it.
An identified officialSend in X-DEN-End-User the person who is actually making the request.
Protected credentialsThe private key and the secret are not shared or pushed to repositories. If you suspect a leak, revoke them from the application's page.
Certificates kept currentThey last 90 days, with a warning at 15. Issue a new one before it expires: the previous one keeps working during the rotation window.
Don't keep more than neededKeep only what the purpose requires.
Announce changesAn incompatible change to a published API requires a new major version. The previous one is deprecated with a retirement date.
